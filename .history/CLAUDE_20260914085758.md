# FX Compass Pro / Trading Analysis App

## Project Purpose

This is a forex, metals, and indices market-analysis application for retail traders.

It provides educational market analysis, multi-timeframe technical analysis, market context, trade-planning information, backtesting, and paper-trading support.

It is not financial advice, investment advice, brokerage software, or a guaranteed-profit system.

Primary instruments may include:
- EURUSD
- EURJPY
- XAUUSD
- USDJPY
- GBPUSD
- AUDUSD
- USDCHF
- US30

The app may support additional instruments through configuration.

---

## Non-Negotiable Safety Rules

- Never claim or imply a guaranteed win, “sure win,” certain profit, safe trade, or guaranteed accuracy.
- Never use phrases such as “sure win,” “guaranteed BUY,” “guaranteed SELL,” “risk-free,” or “cannot fail.”
- Never hide timeframe conflict.
- Never hide missing, stale, delayed, malformed, or incomplete data.
- Never treat unavailable data as neutral, bullish, bearish, or confirmation.
- Never generate a confirmed trade-ready signal from an open candle.
- Never allow M1 or M5 alone to determine overall market direction.
- Never expose API keys, broker credentials, database secrets, or private account information in frontend code, logs, screenshots, or client responses.
- Never connect to or place real broker orders unless real execution is explicitly requested in a separate approved task.
- Keep analysis, backtesting, paper trading, and real execution strictly separated.
- When uncertain, return WAIT, WATCH, INSUFFICIENT DATA, INVALID, or DATA QUALITY ERROR rather than inventing confidence.

## User-Facing Signal Labels

Do not display a standalone BUY or SELL state.

Use only these user-facing final states:

- WATCH — POTENTIAL BUY
- WATCH — POTENTIAL SELL
- BUY SETUP — WAITING FOR M5/M1 CONFIRMATION
- SELL SETUP — WAITING FOR M5/M1 CONFIRMATION
- BUY READY
- SELL READY
- BUY READY — COUNTERTREND WARNING
- SELL READY — COUNTERTREND WARNING
- FULLY ALIGNED BUY READY
- FULLY ALIGNED SELL READY
- WAIT — NO VALID SETUP
- INSUFFICIENT DATA
- DATA QUALITY ERROR
- INVALID
- EXPIRED

Definitions:

- WATCH: Conditions are developing. There is no entry permission.
- BUY SETUP / SELL SETUP: Main directional conditions exist, but entry confirmation is incomplete.
- BUY READY / SELL READY: All configured entry conditions currently pass. This is not a guarantee.
- FULLY ALIGNED BUY READY / SELL READY: Main conditions, entry conditions, MN, and W1 all align.
- Countertrend warning: Main and entry conditions pass, but MN and/or W1 context conflicts.
- WAIT: No valid setup exists.
- INVALID: A calculation, validation, or data error occurred.
- EXPIRED: The setup was valid previously but is no longer valid.
- INSUFFICIENT DATA: Required data is unavailable or insufficient to calculate a valid result.

Never use a green BUY or red SELL badge for WATCH, SETUP, INVALID, EXPIRED, DATA QUALITY ERROR, or INSUFFICIENT DATA.

## Timeframe Stack

Analyze the following nine timeframes whenever data is available:

- MN — Monthly
- W1 — Weekly
- D1 — Daily
- H4 — 4-hour
- H1 — 1-hour
- M30 — 30-minute
- M15 — 15-minute
- M5 — 5-minute
- M1 — 1-minute

Timeframes must be centrally configurable, but all nine are enabled by default.

Every timeframe must be:

- Fetched.
- Validated.
- Calculated.
- Timestamped.
- Displayed in the analysis report.
- Included in the immutable signal audit trail when available.

Do not silently ignore a timeframe.

`NOT_CONFIGURED` is allowed only when the active strategy intentionally disables a timeframe. It must never mean “this timeframe disagrees with the signal.”

## Timeframe Roles

### MN and W1: Broad Context

- MN and W1 are broad market-context timeframes.
- Always fetch, validate, calculate, and display them when data exists.
- They do not automatically block an intraday BUY READY or SELL READY merely because they disagree.
- Their disagreement must:
  - Be prominently visible.
  - Prevent the label “FULLY ALIGNED.”
  - Reduce setup-quality scoring.
  - Trigger a countertrend warning.
  - Be stored in the signal audit trail.
- MN/W1 alignment is required for FULLY ALIGNED BUY READY or FULLY ALIGNED SELL READY.
- A configurable hard-block rule may reject a countertrend trade-ready state when:
  - MN and W1 strongly oppose the proposed direction;
  - D1 and H4 also strongly oppose the proposed direction; and
  - There is no explicitly defined and tested reversal structure.

### D1 and H4: Primary Directional Context

- D1 and H4 have the highest weighting in the main confirmation layer.
- Strong conflict between D1/H4 and the proposed direction normally produces WATCH or WAIT.
- A BUY READY or SELL READY against both D1 and H4 requires an explicit, documented, tested reversal exception.
- Never treat a lower-timeframe Stochastic extreme as enough to override D1/H4 direction by itself.

### H1, M30, and M15: Main Operational Confirmation

- H1, M30, and M15 confirm the main direction, momentum, structure, and trade location.
- They should generally support D1/H4 for trend-following setups.
- Strong disagreement within D1, H4, H1, M30, and M15 normally results in WATCH or WAIT.

### M5: Entry Confirmation

- M5 confirms the intended entry direction after a valid main setup exists.
- M5 cannot independently create BUY READY or SELL READY.
- M5 confirmation must be based on valid closed-candle conditions unless explicitly marked provisional.

### M1: Final Execution Trigger

- M1 is for entry timing only.
- M1 must not determine market bias or override higher-timeframe structure.
- M1 confirmation requires closed-candle validation unless the system explicitly marks the state PROVISIONAL.
- M1 triggers must expire quickly according to configurable rules.

## Stochastic Strategy Rules

Use the Stochastic Oscillator with the following settings on all nine timeframes:

- %K period: 25
- Slowing: 2
- %D period: 4
- Important levels: 20, 30, 70, 80

For each timeframe, calculate and store:

- Current %K.
- Current %D.
- Previous %K.
- Previous %D.
- %K slope.
- %D slope.
- %K/%D crossover direction.
- Threshold-cross/reclaim direction.
- Candle-close status.
- Calculation timestamp.
- Stochastic state.

Use these Stochastic states:

- EXTREME_OVERSOLD
- EXTREME_OVERBOUGHT
- CURLING_UP
- CURLING_DOWN
- K_D_CROSS_UP
- K_D_CROSS_DOWN
- THRESHOLD_RECLAIM_UP
- THRESHOLD_RECLAIM_DOWN
- CONFIRMED_BULLISH
- CONFIRMED_BEARISH
- NEUTRAL
- INCONCLUSIVE

BUY interpretation:

- Oversold context: %K and/or %D is below 20 or 30.
- Curling upward: Stochastic direction turns upward after an oversold condition.
- K/D cross up: %K crosses above %D.
- Threshold reclaim: %K closes back above 20 or 30.
- Stronger confirmation: valid bullish price action, valid structure, valid trade location, and closed candles.

SELL interpretation:

- Overbought context: %K and/or %D is above 70 or 80.
- Curling downward: Stochastic direction turns downward after an overbought condition.
- K/D cross down: %K crosses below %D.
- Threshold break: %K closes back below 80 or 70.
- Stronger confirmation: valid bearish price action, valid structure, valid trade location, and closed candles.

Critical rules:

- An overbought reading is not automatically a SELL.
- An oversold reading is not automatically a BUY.
- A K/D cross alone is not a trade signal.
- A threshold reclaim/break alone is not a trade signal.
- Stochastic signals must be interpreted with market structure, price action, location, volatility, and risk planning.
- Do not require all nine timeframes to be overbought or oversold at exactly the same moment.
- Use the defined hierarchy: MN/W1 context, D1–M15 confirmation, M5 entry confirmation, M1 execution timing.

## Signal Decision Model

The analysis engine must separately calculate:

1. Broad context:
   - MN result.
   - W1 result.
   - Context alignment or conflict.

2. Main confirmation:
   - D1.
   - H4.
   - H1.
   - M30.
   - M15.

3. Entry confirmation:
   - M5.

4. Execution trigger:
   - M1.

5. Final result:
   - Signal label.
   - Alignment status.
   - Setup quality.
   - Risk status.
   - Data-quality status.
   - Explanation.

The app must distinguish:

- Fully aligned setup.
- Trend-following setup.
- Countertrend setup.
- Developing setup.
- Invalid setup.
- Expired setup.
- No setup.

Never call a signal “fully aligned” when MN or W1 conflicts with the final direction.

## Signal Validation Gate

Run this validation gate after every signal calculation and before rendering a final signal, triggering a notification, recording a paper trade, or allowing trade planning.

### WATCH

WATCH may show partial information, but it must clearly identify:

- Missing data.
- Delayed data.
- Stale data.
- Open candles.
- Unconfirmed indicators.
- Conflicting timeframes.
- Incomplete entry conditions.

### BUY SETUP / SELL SETUP

Require:

- Valid D1, H4, H1, M30, and M15 data.
- No blocking data-quality error.
- Valid price action and market-structure conditions.
- Valid technical and Stochastic conditions.
- No invalid or expired trade location.

### BUY READY / SELL READY

Require:

- A valid BUY SETUP or SELL SETUP.
- Valid M5 entry confirmation.
- Valid M1 execution trigger.
- Closed candles for all required confirmation rules.
- Valid entry price or entry zone.
- Valid stop-loss.
- Valid invalidation level.
- Correct target ordering.
- Correct risk-to-reward calculations.
- Acceptable spread.
- No active high-impact-news block.
- Acceptable provider-versus-broker price difference when broker data is available.
- Signal has not expired.
- Price has not already moved beyond the entry acceptance rule.

### FULLY ALIGNED BUY READY / SELL READY

Require all BUY READY / SELL READY conditions plus:

- Valid MN and W1 data.
- MN and W1 aligned with the final signal direction.

### Rejection Rule

If a validation requirement fails:

- Do not render a trade-ready result.
- Do not send a trade-ready notification.
- Render WAIT, INVALID, INSUFFICIENT DATA, DATA QUALITY ERROR, or EXPIRED as appropriate.
- Log the exact rejection reason in the audit trail.

## Market Data Rules

Twelve Data is an analysis-data provider. It must not be assumed to exactly equal a broker’s executable price.

For all provider data:

- Store source timestamps in UTC.
- Store local receipt timestamps in UTC.
- Convert time only for user display.
- Track data age.
- Track the provider name.
- Track request time, response time, HTTP/WebSocket status, and fallback source.
- Validate schema and required fields.
- Safely handle null fields, missing candles, duplicate candles, out-of-order candles, malformed OHLC values, and incomplete candles.
- Handle rate limits, timeouts, provider errors, reconnects, and stale caches.
- Never treat a failed provider response as neutral or confirmed market analysis.
- Never create a confirmed signal from an unclosed candle.

If live streaming is supported and enabled:

- Track WebSocket connection state.
- Prevent duplicate subscriptions.
- Reconnect safely.
- Clean up subscriptions correctly.
- Fall back to REST only when clearly logged and safely validated.

API keys and provider secrets must remain server-side in environment variables or secure secret storage.

  - Provider price.

  - Broker ask.

- Never claim Twelve Data equals the broker’s execution price.

## Backtesting Rules

Backtesting must:

- Process data strictly candle by candle in chronological order.
- Use only information available at that historical moment.
- Prevent look-ahead bias.
- Prevent indicator repainting.
- Use the same signal-validation rules as live/paper analysis where applicable.
- Include realistic spread, slippage, and commission assumptions.
- Handle stop-loss and take-profit ambiguity when both are reached inside the same candle using a documented conservative rule.
- Store the exact strategy version and parameters used.
- Store every generated signal, entry, exit, invalidation, expiry, and rejection reason.

Backtest results must include:

- Number of trades.
- Win rate.
- Gross profit.
- Gross loss.
- Net return.
- Profit factor.
- Average win.
- Average loss.
- Expectancy.
- Maximum drawdown.
- Maximum losing streak.
- Results by session.
- Results by day.
- Results around high-impact news.
- Results when MN/W1 agree.
- Results when MN/W1 conflict.
- Results by final signal state.
- Results by instrument.
- Results by strategy version.

Never describe backtest results as a guarantee of future results.

## Paper Trading Rules

Paper trading must:

- Never place real orders.
- Keep paper-trading data separate from backtests and live integrations.
- Record simulated entry, stop-loss, targets, spread, slippage, and commission assumptions.
- Track signal expiry and invalidation.
- Allow the user to accept, reject, or ignore signals.
- Record the user’s decision and optional reason.
- Clearly label all results as simulated.

1. Inspect the relevant code.
2. State the intended change.
3. Identify affected components, data models, APIs, and tests.
4. Identify risks and assumptions.
5. Create or update tests.
6. Implement the smallest safe change.
7. Run relevant tests, linting, type checks, and build checks.

- Changing core strategy rules.
- Changing Stochastic parameters.

Keep changes focused. Do not refactor unrelated code while implementing a feature unless necessary and explained.
